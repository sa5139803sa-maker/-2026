## 2. خط الأساس: ما نملكه الآن

تمت مراجعة مستودع GitHub عند Commit `a54d134a690b226d48e7975c16afc5e21fd3d093` بتاريخ 2026-11-04. هذه مراجعة ملفات ساكنة؛ لم يُنفذ بناء أو اختبار تشغيلي ضمن هذا الفحص.

### 2.1 الموجود فعليًا
- مشروع Expo/React Native/TypeScript في جذر المستودع.
- مسارات تسجيل الدخول والتوجيه وشاشات رئيسية ضمن `app/`.
- تحميل IBM Plex Sans Arabic بأوزان 400 و500 و600 و700.
- ملف `constants/theme.ts` يحتوي على معظم ألوان الهوية والمسافات والزوايا.
- مكونات واجهة أولية في `components/UI.tsx` وعلامة مائية أولية في `components/BrandMark.tsx`.
- إعداد عميل Supabase ومزود مصادقة في `lib/`.
- إدارة أولية للغواطس والمشتركين في شاشة الإدارة.
- لوحة المتابعة تقرأ عددي الغواطس والمشتركين من Supabase.
- ترحيلان SQL يؤسسان خمسة جداول: `organizations`, `profiles`, `pumps`, `pump_assignments`, `subscribers`، مع سياسات RLS وصلاحيات أولية.
- وثائق التصور والهوية والوثيقة التقنية الأصلية موجودة في `docs/`.

### 2.2 الموجود لكنه غير مكتمل أو تجريبي
- شاشة التشغيل والعداد والطابور: حالة محلية وبيانات ثابتة، وليست دورة تشغيل محفوظة.
- شاشة التحصيل: نموذج عرض لا يسجل قيدًا ماليًا.
- بوابة المشترك: تعرض بيانات ثابتة ولا تقيد العرض بهوية مشترك حقيقية.
- قائمة «المزيد»: عناصر كثيرة غير موصولة بوظائف.
- مخطط لوحة المتابعة وأحدث العمليات: بيانات تجريبية.
- شاشة الإدارة: تغطي إضافة أولية للغطاس والمشترك، ولا تكمل كل عمليات الإدارة والتعيين والأرشفة والاستيراد.

### 2.3 غير موجود بعد بحسب الملفات التي تمت مراجعتها
- ملفات الشعار النهائية السبعة بصيغة SVG.
- Design System كامل ومفصول إلى tokens للخطوط والمسافات والزوايا والظلال والثيم.
- مكتبة المكونات المشتركة المكتملة.
- تطبيق Next.js مستقل للوحة الإدارة وبوابة المشترك.
- قاعدة الهاتف Expo SQLite/Drizzle ومخطط ترحيل محلي.
- Outbox ومزامنة وتعامل موثق مع التعارضات.
- جداول وقواعد التشغيل والطوابير والجداول الأسبوعية.
- دفتر قيود مالي والتحصيل والإيصالات وإشعارات الدفع.

- اختبارات آلية وCI موثوق يثبت البناء والنوعيات والصلاحيات.

### 2.4 نقاط تحقق قبل اعتبار البيئة جاهزة

## 3. مبادئ ترتيب التنفيذ

1. **حفظ الموجود:** لا نعيد كتابة التطبيق من الصفر. نثبت ما يعمل أولًا ثم ننقل أو نعيد تنظيم الملفات تدريجيًا.
2. **التصميم قبل الوظائف الجديدة:** تثبيت الهوية ونماذج الشاشات يسبق توسيع الوظائف، التزامًا بتوجيه الهوية المعتمد.
3. **الأمان قبل بيانات حقيقية:** لا تُحمّل بيانات إنتاجية ولا تنشر تجربة ميدانية قبل إصلاح المصادقة والعزل وسياسات الخادم.
4. **العمل دون إنترنت جزء من التصميم:** توضع حدود المستودعات والأحداث والمعرّفات منذ البداية، ويُختبر مسار Offline مبكرًا قبل توسيع النظام المالي.
5. **لا بيانات وهمية في الشاشات الإنتاجية:** بيانات العرض التجريبية يجب أن تكون محصورة في fixtures أو Storybook/preview واضح وموسوم.
6. **لا ترحيل إنتاجي دون تحقق:** أي migration تُراجع على قاعدة اختبار/فرع تطوير أولًا، ثم تُفحص السياسات والمستشارون قبل الإنتاج.
7. **بوابات قبول:** لا تنتقل المرحلة إلا بعد تحقق معاييرها، وإغلاق العوائق الحرجة أو توثيق قرار قبولها صراحة.

**بوابة القبول:** يوم تشغيل كامل تجريبي دون إنترنت ثم مزامنته دون فقد أو تكرار؛ إغلاق التطبيق واستعادته لا يفقد جلسة التعبئة؛ التنازع بين جهازين ظاهر وممنوع من التحول إلى بيانات مؤكدة صامتة.

### المرحلة 6 — المالية ودفتر القيود والتحصيل
**الحالة:** لم تبدأ؛ شاشة التحصيل الحالية عرض تجريبي.

المهام:
- [ ] تصميم accounts وaccount_transactions وtransaction_allocations وcollections وreceipts وغيرها حسب النموذج المعتمد.
- [ ] دعم الحساب العام للمؤسسة وحساب مستقل لكل غطاس.
- [ ] دفتر قيود لا يعدّل الأرصدة مباشرة؛ الرصيد يستنتج من القيود المؤكدة.
- [ ] تسجيل القبض مع طريقة الدفع ورقم إيصال فريد ومفتاح منع التكرار.
- [ ] تخصيص الدفعات إلى مستحقات المشترك.
- [ ] دعم الإيرادات والمصروفات والإيداع والسحب والتحويل والرد والتسوية وعكس القيد.
- [ ] منع حذف القيود المعتمدة وتسجيل أثر التصحيح.
- [ ] فصل التحصيل المحلي المعلق عن التحصيل المؤكد مركزيًا.
- [ ] إضافة صلاحيات مالية دقيقة وعدم افتراض أن كل موظف يرى الرصيد أو يستطيع السحب.

**بوابة القبول:** تتطابق أرصدة الحسابات مع دفتر القيود؛ لا يتكرر التحصيل؛ لا يصبح إشعار التحويل تحصيلًا قبل المراجعة؛ التحويل بين الحسابات قيد مزدوج لا دخل/مصروف.

### المرحلة 7 — بوابة المشترك وإشعارات الدفع والرسائل
**الحالة:** لم تبدأ؛ بوابة المشترك الحالية بيانات ثابتة.

المهام:
- [ ] تصميم آلية دخول المشترك بالرقم التعريفي ورقم الجوال وفق القرار المعتمد ودون OTP.
- [ ] Edge Function لمقاومة التخمين وتحديد المحاولات وإصدار جلسة محدودة لا تكشف وجود رقم المشترك.
- [ ] إتاحة بيانات المشترك صاحب الجلسة فقط.
- [ ] إنشاء إشعار تحويل بحقول طريقة الدفع والبنك/المحفظة والمبلغ وتاريخ الدفع وصورة الإثبات والملاحظات.
- [ ] اعتماد أو رفض الإشعار مع السبب، ثم إنشاء التحصيل والإيصال عند الاعتماد فقط.
- [ ] تخزين خاص للمرفقات وروابط مؤقتة وحذف صورة الإثبات بعد عشرة أيام مع الإبقاء على سجل المراجعة والمالية.
- [ ] بناء قوالب SMS وWhatsApp وتجهيز الرسالة وفتح التطبيق الخارجي، دون الادعاء بأن الرسالة وصلت.

**بوابة القبول:** لا يرى المشترك حسابًا غير حسابه؛ لا يكشف تسجيل الدخول هل الرقم موجود؛ لا تتغير المستحقات قبل الاعتماد؛ ملفات الإثبات غير عامة؛ سجلات الرسائل تصف بدقة ما حدث.

### المرحلة 8 — التقارير والتدقيق والإطلاق
**الحالة:** لم تبدأ.

المهام:
- [ ] التقارير المالية وكشف حساب المشترك والتحصيل والتشغيل والتوقفات والحسابات والرسائل والمستخدمين.
- [ ] مرشحات الفترة والغطاس والمشترك والمستخدم والتفرع وطريقة الدفع.
- [ ] تصدير Excel؛ PDF حسب أولوية الإصدار.
- [ ] audit_logs غير قابلة للتعديل العادي مع old/new values والمستخدم والجهاز والوقت.
- [ ] النسخ الاحتياطي وخطة الاستعادة والتحقق منها.
- [ ] إعداد EAS Development Build واختبار أجهزة Android فعلية.
- [ ] إكمال فحوص أمان RLS والمستشارين والأداء.
- [ ] إزالة البيانات التجريبية والـdebug logs غير المناسبة للإنتاج.
- [ ] إصدار نسخة تجريبية ميدانية، إغلاق العيوب، ثم الإنتاج.

**بوابة القبول:** التقارير تطابق مصادرها؛ صلاحيات كل دور مجربة؛ النسخ الاحتياطي والاستعادة موثقان؛ اجتياز اختبارات التشغيل والمزامنة والمالية؛ لا توجد مفاتيح سرية في الحزمة أو المستودع.

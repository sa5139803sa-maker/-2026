# قواعد العمل والتوثيق المستمر

## 1. قاعدة التوثيق الإلزامي

**عند كل إنجاز يتم توثيقه داخل المشروع.** لا يُكتفى برسالة محادثة أو وصف شفهي.

يجب أن يتضمن كل Commit وظيفي أو تصميمي أو قاعدة بيانات تحديثًا مناسبًا في:
- \`docs/EXECUTION_LOG.md\`: سجل ما تم فعليًا.
- \`docs/EXECUTION_PLAN_AR.md\`: تحديث حالة المهمة والمرحلة والعوائق والخطوة التالية.
- وثيقة الوحدة المعنية عند تغير متطلب أو قرار (الخطة العامة أو الهوية أو مخطط البيانات).

الأفضل أن يكون تحديث السجل والخطة في نفس Commit الخاص بالإنجاز، حتى يبقى الكود وتوثيقه متزامنين.

## 2. حالات المهام المسموحة

| الحالة | متى تستخدم |
|---|---|
| لم تبدأ | لم يبدأ العمل |
| قيد التنفيذ | يجري تنفيذ المهمة ولم تستوف شروط القبول |
| بانتظار قرار/اعتماد | توجد نقطة تحتاج قرار مالك المشروع أو بيئة/صلاحية |
| متوقفة بسبب عائق | لا يمكن المتابعة قبل إزالة عائق موثق |
| جزئية | تم بعض النطاق، لكن لم يتحقق كله |
| مكتملة بالاختبار | التغيير موجود واجتاز الاختبارات المطلوبة وسجل دليله |

لا تستخدم «مكتملة» لمجرد أن الشاشة تظهر أو أن migration أُنشئت.

## 3. دورة العمل لكل مهمة

1. اقرأ الوثائق المرجعية وسجل الحالة الحالية في المستودع.
2. حدد نطاقًا صغيرًا واضحًا، واذكر الملفات المتوقع تعديلها.
3. افحص تأثير التغيير على البيانات والأمان والتوافق.
4. نفذ المهمة دون خلط وظائف غير مرتبطة.
5. شغّل الفحوص المناسبة: typecheck، build، unit/integration tests، اختبارات يدوية، أو فحص RLS حسب نوع التغيير.
6. راجع diff وتأكد من عدم إضافة أسرار أو بيانات إنتاجية أو بيانات تجريبية إلى تدفق الإنتاج.
7. حدث الخطة والسجل، مع Commit SHA ونتائج الاختبارات.
8. إذا فشل الاختبار، وثق الفشل والعائق ولا تعلن نجاح المهمة.

## 4. شروط القبول حسب نوع التغيير

### واجهة وتصميم
- مطابقة دليل الهوية وDesign Tokens.
- RTL صحيح على الهاتف والويب.
- تحقق من مقاسات صغيرة وكبيرة.
- حالات تحميل وفراغ وخطأ واضحة.
- مكونات مشتركة بدل نسخ مكررة.
- لا توجد بيانات تجريبية تظهر للمستخدم في مسار إنتاجي.

### قاعدة بيانات وSupabase
- migration قابلة للتطبيق والتكرار وفق نمط المشروع.
- اختبار على بيئة تطوير/قاعدة اختبار أولًا.
- RLS وصلاحيات GRANT ومفاتيح العلاقات واضحة.
- اختبارات مستخدمين من مؤسستين وأدوار مختلفة.
- لا يوجد service_role أو secret key داخل عميل عام.
- تشغيل مستشاري الأمان والأداء بعد تغييرات المخطط.

### Auth والصلاحيات
- اختبار التسجيل وتأكيد البريد والدخول والخروج وتجديد الجلسة واستعادتها.
- اختبار إلغاء المستخدم أو تغيير دوره.
- التحقق في قاعدة البيانات/الخادم، لا في الواجهة فقط.
- لا تستخدم user-editable metadata لاتخاذ قرار صلاحية.

### التشغيل والمزامنة
- كل حدث له UUID/idempotency key.
- حفظ التوقيتات والأحداث، لا الحالة الظاهرة فقط.
- اختبار انقطاع الإنترنت وإغلاق التطبيق وإعادة فتحه.
- اختبار تكرار الإرسال والتعارض بين الأجهزة.
- لا تتحول العملية المحلية إلى مؤكدة قبل قبول الخادم.

### المالية
- لا تعديل مباشر للأرصدة.
- قيد مزدوج للتحويلات بين الحسابات.
- منع التكرار.
- لا حذف للقيود المعتمدة؛ التصحيح بالعكس/التسوية.
- لا تخفيض للمستحقات بإشعار تحويل غير معتمد.

## 5. قواعد GitHub

- العمل على \`main\` يتم فقط بعد فحص head الحالي وعدم الكتابة فوق تغييرات أحدث.
- استخدم Commit واضحًا ومحدد النطاق.
- لا ترفع \`.env\` أو أسرارًا أو ملفات بناء ضخمة أو بيانات حقيقية.
- لا تحذف ملفات قديمة أو أرشيفات دون توثيق سبب الحذف وحفظ نسخة مطلوبة خارج Git.
- أي تغيير في migrations يرفق باختبار موثق على بيئة غير إنتاجية قبل الدمج.
- بعد كل Commit راجع الملفات والفرع وتأكد من ظهور الوثائق.
- إذا تغيرت المواصفات، أضف قرارًا مؤرخًا بدل تعديل المتطلب بصمت.

## 6. قالب تسليم المهمة

يجب أن يختتم كل تسليم عملي بهذه المعلومات:
- ما الذي اكتمل؟
- ما الملفات التي تغيرت؟
- Commit SHA ورابطه.
- ما الفحوص التي نُفذت ونتيجتها؟
- ما الذي لم يكتمل؟
- ما الخطوة التالية ذات الأولوية؟

**القاعدة النهائية:** لا يُسجل أي إنجاز على أنه مكتمل ما لم يكن موجودًا في المستودع، ومختبرًا بما يناسبه، وموثقًا في سجل الإنجازات.

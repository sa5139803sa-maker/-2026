# مراجعة أمنية ساكنة لقاعدة إدارة المياه

**التاريخ:** 2026-11-04  
**النطاق:** ملفات ترحيلات Supabase الموجودة في Git فقط؛ لا تمثل هذه الوثيقة اختبارًا حيًا لقاعدة بيانات.  
**النتيجة العامة:** لا تعتمد هذه الترحيلات للإنتاج قبل معالجة الملاحظات عالية الخطورة واختبار RLS على مشروع اختبار محدد.

## 1. حالة مشروع Supabase

تم استدعاء قائمة المشاريع المتاحة للاتصال الحالي. ظهرت المشاريع التالية:

لم يظهر مشروع نشط يحمل اسم «إدارة المياه»، كما أن ملف `.env.example` لا يحتوي عنوان مشروع أو مفتاحًا عامًا. اسم المشروع الأول عام ولا يكفي وحده لإثبات أنه قاعدة إدارة المياه؛ لذلك لم يتم اختيار أي مشروع ولم تُنفذ عليه استعلامات أو تغييرات.

## 3. النتائج

### SEC-01 — ربط تعيين الموظف بغطاس من مؤسسة أخرى
**الخطورة: عالية — يمنع اعتماد RLS للإنتاج**

جدول `pump_assignments` يحتوي `pump_id` و`user_id`، لكن سياسات الإدخال والتعديل تتحقق من أن الغطاس تابع لمؤسسة المدير فقط. لا يوجد تحقق مماثل يثبت أن ملف المستخدم المعيّن تابع للمؤسسة نفسها.

النتيجة المحتملة: يستطيع مدير مؤسسة إنشاء علاقة تعيين تشير إلى مستخدم في مؤسسة أخرى، حتى لو لم يتمكن ذلك المستخدم من قراءة العلاقة لاحقًا.

**المعالجة المطلوبة قبل الإنتاج:**
1. فرض تطابق المؤسسة بين الغطاس والمستخدم المعيّن عند INSERT وUPDATE.
2. الأفضل تمثيل نطاق المؤسسة في العلاقة مع قيود مرجعية مركبة أو Trigger تحقق موثوق.
3. إضافة اختبارات سلبية تثبت رفض تعيين مستخدم من مؤسسة B على غطاس مؤسسة A.

### SEC-02 — السماح بربط مشترك بغطاس من مؤسسة أخرى
**الخطورة: عالية — يمنع اعتماد RLS للإنتاج**

جدول `subscribers` يحتوي `organization_id` و`pump_id`، لكن سياسات المدير تتحقق من أن المشترك ضمن مؤسسة المدير ولا تتحقق من أن الغطاس المشار إليه يتبع المؤسسة نفسها. المفتاح الأجنبي الحالي على `pump_id` يتحقق من وجود الغطاس فقط، لا من تطابق المؤسسة.

**المعالجة المطلوبة قبل الإنتاج:**
1. فرض تطابق `subscribers.organization_id` مع مؤسسة `pumps.id` المشار إليه.
2. تنفيذ ذلك بقيد مركب مناسب أو Trigger قبل الكتابة.
3. إضافة اختبارات ترفض ربط مشترك مؤسسة A بغطاس مؤسسة B، بما في ذلك UPDATE.

### SEC-03 — قراءة جميع الغواطس والمشتركين لكل أعضاء المؤسسة
**الخطورة: عالية — تحتاج قرار صلاحيات قبل الإنتاج**

سياسات SELECT الحالية على `pumps` و`subscribers` تسمح لأي عضو في المؤسسة بقراءة جميع السجلات داخلها. هذا أوسع من متطلبات المشروع التي تنص على أن التشغيل وإدارة الموارد تكون «ضمن الصلاحية» وأن المشغّل يتعامل مع الغطاس المخصص له.

**المعالجة المطلوبة قبل الإنتاج:**
1. المدير يرى موارد المؤسسة بحسب صلاحيات الإدارة.
2. المشغّل والمحصّل لا يحصلان إلا على نطاق الغطاس/التعيين المسموح لهما.
3. المشرف يحصل على تقارير القراءة فقط ضمن نطاقه.
4. لا يُعتمد إخفاء الشاشة كبديل عن RLS؛ يجب أن يرفض الخادم والـRLS الاستعلام عن غطاس غير معيّن.

يلزم حسم كيفية تمثيل نطاق المشرف أولًا؛ جدول `pump_assignments` الحالي يحوي الدورين operator وcollector فقط.

### SEC-04 — قراءة ملفات المستخدمين للمدير غير متاحة من سياسة SELECT الحالية
**الخطورة: متوسطة — تؤثر في إدارة المستخدمين**

سياسة `profiles` الحالية تسمح للمستخدم بقراءة ملفه الشخصي فقط. هذا جيد للعزل الذاتي، لكنه لا يتيح للمدير قراءة ملفات الموظفين التابعين لمؤسسته إذا كانت شاشة إدارة المستخدمين ستحتاج ذلك.

**المعالجة المطلوبة:**
- إضافة مسار قراءة محدود للمدير داخل المؤسسة فقط، دون السماح له بتعديل role أو organization_id من العميل.
- يجب تجنب سياسات RLS متكررة ذاتية الاستدعاء عند فحص دور المدير؛ استخدم دالة تفويض آمنة ومحدودة أو تصميمًا لا يسبب recursion.

### SEC-05 — حسم علاقة التعيينات قبل مخطط الصلاحيات النهائي
**الخطورة: قرار تصميم مانع**

تذكر وثائق المشروع الاسمين `user_pump_assignments` و`pump_assignments`. الترحيلات الحالية أنشأت `pump_assignments` فقط. لا ينبغي بناء سياسات التعيين أو مزامنة SQLite أو واجهة إدارة المستخدمين قبل حسم هل العلاقة واحدة أم علاقتان مختلفتان.

## 4. ضوابط إيجابية موجودة بالفعل

- RLS مفعّل على الجداول الخمسة التي أنشأتها الترحيلات.
- لا توجد صلاحيات عامة للجداول على دور `anon`.
- جدول `profiles` لا يمنح العميل صلاحية تعديل `role` أو `organization_id`؛ الصلاحية المباشرة تقتصر على `display_name`.
- دالة `create_organization` تتحقق من `auth.uid()`، وتتحقق من وجود profile غير مرتبط بمؤسسة، وتستخدم قفل الصف قبل إنشاء المؤسسة.
- تم سحب EXECUTE من PUBLIC وanon لدالة `create_organization` ومنحها إلى authenticated فقط.

هذه الضوابط لا تلغي النتائج SEC-01 إلى SEC-04.

## 5. خطة المعالجة المقترحة

1. تحديد مشروع Supabase الصحيح وتنشيطه/إعداده من مالك المشروع؛ لا تستخدم مشروع «بقالتي» أو المشروع العام تلقائيًا.
2. نسخ المخطط إلى بيئة اختبار معزولة وتأكيد إصدار PostgreSQL وData API.
3. حسم علاقة تعيين المستخدم والغطاس ونطاق المشرف.
4. إعداد Migration تصحيحي يفرض تطابق المؤسسة في العلاقات، ويضبط SELECT policies بحسب الدور والتعيين.
5. اختبار عزل المؤسسات A/B واختبارات الدور والغطاس غير المعيّن، ثم تشغيل Supabase Security Advisors.
6. بعد نجاح الاختبارات فقط، اعتماد الترحيل ونشره على المشروع المحدد.

## 6. ما لم يتم

- لم يتم الاتصال بقاعدة بيانات نشطة.
- لم يتم تنفيذ SQL أو apply migration.
- لم يتم تغيير أي RLS policy على خادم.
- لم يتم تشغيل Security Advisors؛ لا يوجد مشروع نشط ومحدد لهذا التطبيق في قائمة الاتصال.
- لم يتم تعديل الأدوار الحالية أو إضافة Super Admin أو Accountant.

**قرار المراجعة:** قبول المراجعة الساكنة فقط. لا تعتبر قاعدة البيانات آمنة للإنتاج حتى إغلاق SEC-01 إلى SEC-04 وتجاوز اختبارات RLS السلبية.
